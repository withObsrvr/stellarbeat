# External history archive probe

## Purpose

Radar reads `<history URL>/.well-known/stellar-history.json` to determine
whether a validator's history archive is current. Some archive operators block
the egress addresses used by the DigitalOcean App Platform. In that case the
archive can return HTTP 401 or 403 to Radar while remaining available to the
rest of the network.

Radar records that result as `historyArchiveAccessRestricted`. It must not
classify the archive as stale or generally unreachable, because the response
only establishes that this scanner was denied.

The external probe described here provides a second observation point outside
DigitalOcean. It is intentionally a small, authenticated service rather than a
general-purpose HTTP proxy.

## Scope

The first version of the probe only checks the archive state document. It does
not replace the history scanner that verifies checkpoint contents.

The probe must:

- run from an egress network independent of the Radar deployment;
- fetch only `/.well-known/stellar-history.json` below a supplied archive URL;
- return the upstream HTTP result and a validated `currentLedger` value;
- enforce strict SSRF, redirect, response-size, and timeout controls;
- expose enough telemetry to distinguish upstream failures from probe failures.

The probe must not:

- accept an arbitrary path, method, headers, or request body;
- forward upstream response bodies without validation;
- turn an HTTP 401 or 403 into evidence that the archive is stale;
- claim that a fresh state document proves the archive is complete or free of
  corrupt checkpoint files.

## API contract

### Request

`POST /v1/archive-state/check`

```json
{
	"archiveUrl": "https://stellar-history.moneygram.com/v1",
	"latestLedger": "64783487",
	"requestId": "01J9..."
}
```

- `archiveUrl` is the base URL declared in the validator's `HISTORY` field.
- `latestLedger` is serialized as a decimal string to avoid integer precision
  loss between runtimes. It is context for logging; Radar remains responsible
  for applying its freshness margin.
- `requestId` is generated by Radar and propagated into logs and traces.

Authenticate calls with a private service credential. A short-lived signed token
or platform service identity is preferred. If an HMAC is used, sign the
timestamp and exact request bytes, reject timestamps older than 60 seconds, and
reject replayed request IDs.

### Successful probe response

```json
{
	"requestId": "01J9...",
	"outcome": "ok",
	"archiveUrl": "https://stellar-history.moneygram.com/v1",
	"stateUrl": "https://stellar-history.moneygram.com/v1/.well-known/stellar-history.json",
	"currentLedger": "64783487",
	"httpStatus": 200,
	"cacheMaxAgeSeconds": null,
	"checkedAt": "2026-10-05T12:29:04.000Z",
	"durationMs": 184
}
```

`currentLedger` must be returned as a decimal string. The probe must parse the
JSON and reject a missing, negative, fractional, or unsafe ledger value.

### Non-successful probe response

The service itself should still return HTTP 200 when it completed the upstream
check. `outcome` describes the upstream result:

```json
{
	"requestId": "01J9...",
	"outcome": "access_restricted",
	"archiveUrl": "https://stellar-history.moneygram.com/v1",
	"stateUrl": "https://stellar-history.moneygram.com/v1/.well-known/stellar-history.json",
	"httpStatus": 403,
	"cacheMaxAgeSeconds": null,
	"checkedAt": "2026-10-05T12:29:04.000Z",
	"durationMs": 91
}
```

Allowed outcomes are:

| Outcome             | Meaning                                                  |
| ------------------- | -------------------------------------------------------- |
| `ok`                | HTTP 200 with a valid state document                     |
| `access_restricted` | Upstream returned HTTP 401 or 403                        |
| `unreachable`       | DNS, connection, TLS, or timeout failure                 |
| `invalid_response`  | HTTP response or body cannot be used as an archive state |

Use HTTP 4xx for an invalid probe request or failed authentication, and HTTP 5xx
when the probe service itself cannot perform the check. These are probe failures
and must not be confused with upstream outcomes.

## Radar integration

The initial integration should use the probe as a targeted fallback:

1. Radar performs its normal direct request.
2. A direct HTTP 401 or 403 records `access-restricted` and invokes the probe.
3. If the probe returns `ok`, Radar applies the existing ledger freshness and
   cache-control rules to the probe result.
4. If the probe also returns `access_restricted`, Radar retains
   `historyArchiveAccessRestricted=true`.
5. Probe unavailability does not change the direct observation into `stale` or
   `unreachable`. Radar retains `access-restricted` and logs that secondary
   verification was unavailable.

The fallback should have a bounded concurrency and a total deadline so a probe
outage cannot push the network scan beyond its execution window. Cache a valid
probe response only within the normal scan interval, and include its age in
logs. Do not reuse a previous scan's success as current evidence.

The API field exposed by Radar is:

```json
{
	"historyArchiveAccessRestricted": true,
	"historyArchiveUnreachable": false,
	"isFullValidator": false
}
```

Until a probe succeeds, the UI should say **History archive access restricted
for Radar scanner**. It should not say that the archive is behind.

## Network and SSRF controls

Archive URLs originate in public TOML files and are therefore untrusted input.
Before every request, including each redirect, the probe must:

- allow only `https` (permit `http` only if Radar explicitly retains support for
  legacy archives);
- reject embedded credentials, fragments, and non-HTTP schemes;
- normalize the base URL and append the fixed state-document path itself;
- resolve the hostname and reject loopback, private, link-local, multicast,
  carrier-grade NAT, documentation, and cloud-metadata address ranges for IPv4
  and IPv6;
- connect only to an address returned by the validated DNS lookup, preventing
  DNS rebinding between validation and connection;
- either disable redirects or allow at most two redirects after fully
  revalidating the destination;
- cap the response body at 64 KiB and accept JSON only;
- use a connection timeout of 3 seconds and a total request deadline of 8
  seconds;
- send no cookies, user-supplied headers, or internal credentials upstream.

Rate-limit callers and cap global and per-host concurrency. The service must
never expose a public unauthenticated endpoint that can fetch arbitrary hosts.

## Deployment

Deploy the probe in a provider or region with egress independent from
DigitalOcean. A small AWS Lambda/API Gateway service, container on Fly.io, or a
locked-down Cloudflare Worker can satisfy the requirement. Confirm the chosen
provider is not blocked by the known restricted archives before adopting it.

Use at least two instances or a serverless deployment with no single mutable
host. Keep the service stateless. Store credentials in the platform secret
manager, require TLS, and restrict ingress to authenticated Radar calls where
the platform supports it.

## Observability

Emit structured logs containing:

- request ID and a normalized archive host;
- outcome and upstream HTTP status;
- DNS, connect, TLS, first-byte, and total duration where available;
- response size and parsed ledger, but never the complete response body;
- redirect count and final validated host;
- deployment region and probe version.

Metrics should include request counts and latency by outcome, upstream host, and
probe region. Alert on probe-wide failure rate, authentication failures,
deadline exhaustion, and a sudden increase in `access_restricted` outcomes.

## Acceptance tests

Before enabling the fallback in production, verify that:

- a known archive returns `ok` with its ledger and cache policy;
- a test endpoint returning 401 and 403 maps to `access_restricted`;
- DNS, TCP, TLS, and timeout failures map to `unreachable`;
- malformed JSON and an invalid ledger map to `invalid_response`;
- private addresses, redirects to private addresses, IPv6 local addresses, and
  DNS-rebinding fixtures are rejected;
- oversized and slow responses are terminated;
- an unavailable probe cannot make the main scan exceed its deadline;
- a probe success changes the Radar result from access-restricted to the
  appropriate up-to-date or stale result.
